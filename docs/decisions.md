# Журнал инженерных решений и замеров (chumba)

Документ фиксирует, **почему** стек выглядит именно так: какие варианты рассматривались,
что показали замеры на реальном стенде (Windows + Docker Desktop + RTX 5060 Ti 16 ГБ),
и какие компромиссы приняты. Все цифры — из логов и прогонов от 02.10.2026.

---

## 1. Инференс: llama.cpp, образ и драйвер

**Решение:** `ghcr.io/ggml-org/llama.cpp:server-cuda13`, пин по digest; драйвер обновлён до 617.14.

**Почему:** первый запуск `server-cuda13` упал с `nvidia-container-cli: unsatisfied condition:
cuda>=13.4` (драйвер 591.86 давал CUDA 13.1). Варианты: (а) откатиться на `server-cuda` (CUDA 12),
(б) обновить драйвер. Выбрано (б): свежие сборки критичны для новых архитектур (sm_120) и
tool calling. После обновления драйвера GPU-хук падал в `dlopen(NVML)` — вылечено полным
перезапуском WSL (`docker desktop restart`), т.к. `/usr/lib/wsl/lib` оставался от старого драйвера.

**Цена:** оба образа скачаны (~несколько ГБ); обновление драйвера потребовало перезапуска Docker.

## 2. Публикация портов: socat-форвардеры

**Проблема:** контейнеры, подключённые **только** к `internal: true` сети, не публикуют порты
на host в Docker Desktop (проверено экспериментом: `NetworkSettings.Ports` пуст; после
подключения обычной сети порт появляется).

**Решение:** тонкие socat-форвардеры (`llama-port`, `openwebui-port`, `delegate-port`,
`embeddings-port`) на сетях `llm_internal + edge`. Целевые сервисы остаются без egress.

**Отвергнуто:** подключать сами сервисы к egress-сети (дало бы им интернет-маршрут и сломало
структурную изоляцию).

## 3. MCP и Open WebUI

**Решение:** нативный MCP Open WebUI (≥0.6.31, Streamable HTTP) + `ihor-sokoliuk/mcp-searxng`
в HTTP-режиме с `MCP_HTTP_HARDEN`.

Найденные по ходу факты (все — эмпирически, по коду контейнера):

- id инструмента собирается как `server:mcp:{info.id}` — при сохранении подключения через API
  `info` пуст, и модель «не видит» инструменты. Лечение: заполнять `info.id` при создании.
- для MCP-подключений используется **полный URL** (`http://search-mcp:8080/mcp`), поле `path`
  обязательно схемой, но игнорируется.
- hardened-режим проверяет Host: добавление `127.0.0.1:8085` в `MCP_HTTP_ALLOWED_HOSTS`
  понадобилось для host-тестов; делегат ходит по имени `search-mcp:8080`.
- MCP-клиент `mcp` 2.x переименовал `FastMCP` → `MCPServer` и сменил клиентский API.
  Код написан под v1 → пин `mcp<2` (официальная рекомендация из текста ошибки).
- клиентский SDK v1 конфликтовал с SSE-стримом Node-сервера (`BrokenResourceError`),
  поэтому `delegate` ходит в MCP **сырым JSON-RPC** (initialize → notifications → tools/call),
  как и проверочный `check_mcp.py`.

**Отвергнуто:** MCP-клиент в web-UI самого llama.cpp (только stdio; в контейнере нет node/python);
`mcpo` (не нужен при нативном MCP); Danmoreng/websearch-mcp (2★, только HTTP, нет `web_url_read`).

## 4. Делегирование: одноразовый вызов, `urls`, санитайзер

**Решение:** `delegate_to_worker(task, urls?, max_sources)` — локальные поиск/чтение + **один**
вызов облака + строгий JSON; никакого агентного цикла в облаке.

**Почему:** один исходящий payload на задачу → полный аудит (JSONL), минимум egress и круговых
задержек; воркер не «бродит» по сети от вашего имени.

**`urls`:** добавлено для научного сценария — оркестратор сам находит статью и просит изучить
именно её (в журнале поле `explicit_urls`).

**Санитайзер:** перед облаком локальная модель (thinking off, ~0.5 с) переписывает задачу;
`DELEGATE_SANITIZE_FAIL=reject` — при сбое рерайта задача не уходит вообще. Проверено:
маркер `LEAK_MARKER_*` и имя из задачи в payload не попали (`SANITIZE_OK=True`).

**Результат E2E:** 12.5 с на цепочку (поиск → чтение 2 страниц → облако → JSON с 4 фактами);
позже — научный прогон с 3 делегированиями и резюме с OR/95% ДИ.

## 5. Контекст и ресурсы

### 5.1 16k → 32k: KV на GPU, а не в RAM

| Гипотеза | Замер | Вердикт |
|---|---|---|
| KV в RAM (`LLAMA_ARG_KV_OFFLOAD=false`), 32k | VRAM −1.6 ГБ, но генерация **6.7–8.1 т/с** (против ~20) | ❌ невыгодно |
| KV на GPU, 32k | VRAM 15.6 / 16.3 ГБ, prefill ~860 т/с, генерация ~19.7 т/с | ✅ принято |

Причина: у модели hybrid attention KV-кэш маленький (~350–700 МБ на 16–32k), поэтому «экономия»
на RAM не стоила трёхкратной просадки скорости. Промпт 18 464 токена из ошибки
`exceed_context_size_error` превратился в штатный запрос (17 796 токенов, 21 с).

Фоллбэки задокументированы: ctx 24576 → 16384; KV в RAM — только если VRAM впритык.

### 5.2 Сон на простое

`--sleep-idle-seconds` (600 с): модель выгружается, **VRAM 15.2 → 1.7 ГБ**, RAM: свободно
13.5 ГБ; `/health`, `/props`, `/models` не будят. Пробуждение по запросу — 87–149 с (запрос
блокирующе ждёт). Это выбрано вместо llama-swap/самописного watchdog: одна встроенная опция,
ноль новых сервисов.

### 5.3 Router-режим (лечение «Модель не найдена»)

**Симптом:** после простоя UI терял и `orchestrator`, и `chumba-orchestrator`.
**Причина:** в single-model режиме во время сна/загрузки `/v1/models` и `/props` отдают
`503 Loading model`; Open WebUI при обновлении чистит список моделей.
**Решение:** router-режим (`--models-preset llama/models.ini`, секция `[orchestrator]`).
Проверено: во сне `/v1/models` перечисляет модель, Open WebUI сохраняет оба id; во время
пробуждения список тоже стабилен. Health в router-режиме отвечает мгновенно (5 с), модель
догружается в фоне.

### 5.4 Сжатие истории и RAG

- **Rolling summary** (фильтр Open WebUI): порог 12k токенов, сохраняются последние 6 сообщений,
  конспект ≤400 токенов, кэш в data-томе, fail-open. Тест: `summarizing 2851 chars` → `cache hit`.
- **RAG:** выбрана bge-m3 (MIT, 0.6B, 1024-dim, мультиязычная) на **CPU** — чтобы не отбирать VRAM
  у оркестратора. Качество: RU↔EN близость 0.93 против 0.42 у несвязанных. Open WebUI переведён
  с встроенного движка (требовал HF-загрузку, а у UI нет egress) на наш эндпоинт; настройки —
  persistent ConfigVar, поэтому применяются скриптом через API.

## 6. Egress: DNS, антибот, Tor, поисковые движки

### 6.1 DNS-заглушки провайдера

`github.com`, `en.wikipedia.org`, `www.reddit.com` резолвились в `198.18.0.0/15` (заглушки
DPI-блокировок), и `mcp-searxng` корректно блокировал такие URL («blocked by security policy»).
Решение: публичные резолверы `dns: [1.1.1.1, 8.8.8.8]` для `searxng`, `search-mcp`, `byparr`.
Эффект: github/wikipedia из «156 символов» стали полными (8000).

### 6.2 Byparr (stealth-браузер)

Проверено API и логами: Cloudflare-тест `nowsecure.nl` пройден; чтение github/wikipedia/habr —
8000 символов; reddit — полная страница (~92 с). Ограничения Byparr признаны заранее: гарантий
нет, тяжёлые CF-сайты медленные, escape hatch — `BYPARR_PROXY` (резидентный прокси).

### 6.3 Tor

Выбран `PeterDaveHello/tor-socks-proxy` (GPL-3.0, ~10 МБ) и официальный паттерн SearXNG
(`socks5h://`, `using_tor_proxy`, `extra_proxy_timeout`). **В проверенной сети Tor блокируется
DPI**: bootstrap застревает на 10%, десятки TLS-handshake фейлов. Сервис оставлен в профиле
`tor` (по умолчанию выключен) — включается одной командой там, где Tor доступен или появятся мосты.

### 6.4 Отказоустойчивость поиска

Инцидент: в реальном чате brave/DDG/google cse одновременно ушли в лимиты — поиск и делегат
получали «no results» (единая точка отказа). Меры:

- включены резервные general-движки **bing, mwmbl, yandex, yep** (проверено: 68 результатов,
  пока основные и yandex лежали);
- у делегата — цепочка **SearXNG → science-категория → Europe PMC REST** (проверено: 478 хитов
  «eprenetapopt TP53»); путь пишется в журнал (`search_path`).

### 6.5 Научный пайплайн

PubMed-страницы отдают «включите cookies» и 403. Решение: маппинг `pubmed.ncbi.nlm.nih.gov/<PMID>`
→ **NCBI E-utilities `efetch`** (`retmode=text`) с фоллбэком на Europe PMC API и оригинал.
Проверено на живой статье: субагент извлёк аннотацию и построил факты с confidence. Промпт
`chumba-orchestrator` дополнен правилами: деградация поиска (1–2 переформулировки → PubMed → delegate),
сверка номенклатуры препаратов по PubMed.

## 7. Сводка конфигурационных решений

| Параметр | Значение | Почему |
|---|---|---|
| `ORCHESTRATOR_CTX` | 32768 | влезает с KV q4_0 на GPU; 2× к прежнему окну |
| `LLAMA_ARG_KV_OFFLOAD` | true | KV в RAM даёт −1.6 ГБ VRAM, но −3× скорости |
| `SLEEP_IDLE_SECONDS` | 600 | баланс «не дёргать модель» / «освободить ресурсы общего ПК» |
| `ORCHESTRATOR_PARALLEL` | 1 | один пользователь; целостность слота |
| `SEARCH_RESULTS_COUNT` / `DELEGATE_READ_TOP` | 4 / 2 | бюджет контекста и времени чтения |
| `WORKER_MAX_SOURCE_TOKENS` / `WORKER_MAX_RESULT_TOKENS` | 3000 / 800 | промпт воркера и ответ JSON ограничены |
| `DELEGATE_SANITIZE` / `FAIL` | llm / reject | принудительная обезличка; сбой = отказ отправки |
| `RAG_TOP_K` | 4 | retrieved-контекст ≤ ~2–3k токенов |
| `BYPARR_TIMEOUT_SECONDS` / concurrency | 120 / 2 | тяжёлые CF-сайты; контроль RAM Firefox |
| Резервные движки | bing, mwmbl, yandex, yep | поиск не умирает при лимитах основных |
